# ADR-0015. Windows의 Office 미리보기는 미리보기 처리기를 앱 창 위에 네이티브 창으로 겹쳐 보여 준다

- 상태: Accepted
- 날짜: 2026-10-09

## 맥락

macOS는 Office 문서를 Quick Look이 만든 HTML로 실제 문서 모습 그대로 보여 준다([ADR-0014](0014-macos-office-quicklook-preview.md)). Windows는 데이터 미리보기(`preview.office`, 기본 꺼짐)뿐이라 서식·배치·그림이 없다. 사용자는 Windows에서도 맥의 Quick Look처럼 문서를 보기를 원했다.

Windows에는 Quick Look에 해당하는 공개 명령이나 HTML 변환기가 없다. 대신 탐색기의 미리보기 창이 쓰는 **미리보기 처리기**(`IPreviewHandler`)가 있다. Office가 설치돼 있으면 docx·xlsx·pptx(와 구형·매크로 형식)에 등록돼 있고(이 PC: `HKCR\.docx\shellex\{8895b1c6-b41f-4c1c-a562-0d564250836f}`), 처리기는 문서를 HTML이 아니라 **주어진 창 안에 직접 그린다**. 앱 화면은 웹뷰라 그 창을 웹 안에 넣을 수 없다.

## 결정

- Windows에서는 **docx만** `preview.office` 설정과 관계없이 미리보기 처리기로 보여 준다. xlsx·pptx를 포함한 그 밖의 형식과 압축 파일 안의 문서는 지금까지의 미리보기(데이터 미리보기, 설정 `preview.office`)를 쓴다(ADR-0014와 같다). 처음에는 macOS Quick Look과 같은 목록(docx·xlsx·pptx, doc·xls·ppt, docm·xlsm·pptm)을 대상으로 했으나, 사용자 확인에서 pptx는 **처리기가 스크롤바만 그리고 슬라이드는 그리지 않았고**(원인을 찾지 못함) xlsx도 인터넷에서 받은 파일의 차단 문제로 확인이 끝나지 않아 사용자가 docx만 쓰기로 정했다(2026-10-09). 코드는 `lib/office/kinds.ts`의 `usesPreviewHandler` 한 곳에서 이 목록을 정하므로, 형식을 더하려면 거기만 고치면 된다.
- 처리기는 앱 창의 **자식 네이티브 창**으로 띄워 웹뷰의 미리보기 영역 위에 겹친다. 창 하나마다 전용 STA 스레드가 처리기와 자식 창을 맡고(메시지 루프 필요), 호출하는 쪽은 시간 제한(20초)을 두고 기다리므로 처리기가 멈춰도 앱 스레드는 멈추지 않는다. 처리기는 서로게이트(`prevhost`)로 프로세스 밖에서 먼저 띄우고, 안 되면 프로세스 안에서 띄운다.
- 웹이 미리보기 영역의 위치·크기(웹뷰 기준 CSS 픽셀)를 Tauri 명령으로 알려 주면, Rust가 화면 배율을 곱해 물리 픽셀로 바꿔 자식 창을 옮긴다. 항목을 빠르게 넘길 때는 150ms 동안 항목이 그대로일 때만 띄운다.
- 입력: 마우스(휠·클릭·스크롤바)는 처리기 창이 받아 문서를 스크롤한다. 키보드는 앱에 남는다. 호스트 창이 `WM_PARENTNOTIFY`로 문서를 눌렀음을 알면 앱이 웹뷰로 포커스를 되찾아 ↑↓·Esc가 계속 앱에서 동작한다.
- 겹침: 네이티브 창은 웹 요소 위에 그려지므로, 대화상자·메뉴·컨텍스트 메뉴·팔레트·파일 찾기·설정·도움말·작업 큐·드래그·탭 끌기가 떠 있는 동안, 그리고 미리보기 창을 끌거나 크기를 바꾸는 동안 처리기 창을 숨긴다. 문서는 다시 읽지 않고 닫히면 다시 보인다.
- 처리기가 등록돼 있지 않거나(Office 미설치 등) 문서를 못 그리면 호출 쪽이 지금까지의 미리보기(설정 `preview.office`)로 돌아간다. 못 그린 경우에는 오류 문구(처리기 ID와 영역 크기 포함)를 폴백 화면 맨 위에 보여 준다.
- **인터넷에서 받은 파일(차단 표시 `Zone.Identifier`의 `ZoneId` 3 이상)은 Office 처리기가 미리보기를 막는다**(2026-10-09 사용자 확인으로 드러남: 처리기가 `DoPreview`에서 `0x80004005`를 내고, 같은 파일의 표시 없는 복사본은 그려진다. 탐색기 미리보기 창이 다운로드한 문서를 막는 것과 같다). 그래서 그리기 전에 표시를 읽어 "인터넷에서 받은 파일이라 Office가 미리보기를 막습니다"라고 알리고, **사용자가 "차단 해제하고 보기" 버튼을 누를 때만** 그 파일의 `Zone.Identifier`를 지운 뒤(탐색기 파일 속성의 "차단 해제"와 같다, 파일 내용은 그대로) 처리기로 다시 보여 준다. 누르기 전에는 파일을 바꾸지 않고 폴백 미리보기를 쓴다.

## 결과

- 장점: 새 번들이나 외부 변환기 없이, 사용자 PC의 Office가 그리는 실제 문서 모습을 쓴다. 구형·매크로 형식도 같은 처리기가 다룬다. 문서를 읽는 일을 별도 프로세스(`prevhost`)가 하므로 악성·망가진 문서의 영향이 앱 밖에 머무르는 편이다.
- 단점:
  - 네이티브 창이라 웹 화면과 따로 논다. 위에 뜨는 요소를 우리가 일일이 알아야 숨길 수 있다(목록에 없는 새 겹침이 생기면 문서가 그 위에 보인다). 문서 안 글자 선택·복사 같은 키 조작은 되지 않는다.
  - 모습은 설치된 Office와 처리기에 달렸다(보호된 보기 안내, 구형 형식 변환 등). 확인하지 못한 Office 버전이 있다.
  - 처리기가 첫 항목에서 프로세스를 띄우느라 느릴 수 있다.
  - 다운로드한 파일 대부분이 차단돼 있어, 차단 해제 없이는 이 기능이 보이지 않는다. 차단 표시는 Office의 보호된 보기가 쓰는 보안 장치이므로, 차단을 풀면 그 파일을 그 보호 없이 처리기가 읽는다(사용자가 직접 누를 때만 풀리는 이유).
  - Windows 11의 Office가 처리기를 다른 CLSID로 등록하거나 등록하지 않는 구성은 확인하지 못했다. 그때는 데이터 미리보기로 돌아간다.
  - 두 OS의 미리보기 방식이 다르다([ADR-0013](0013-lookup-query-syntax.md)의 "3개 OS에서 같게 동작" 원칙에 대한 두 번째 의식적 예외).
- 검증: 실제 Word 처리기로 docx를 그려 보는 Windows 전용 통합 테스트(`preview_host`)가 있고(Office가 없으면 건너뜀), 처리기 찾기·좌표 변환·웹 쪽 표시·숨김 흐름은 단위 테스트가 있다. 포커스·배율·창 이동 같은 네이티브 동작은 실제 앱에서 사람이 확인한다.
- 후속 작업: 겹침 목록에 없는 새 요소가 생기면 `PreviewHandlerView`의 `covered`에 더한다. 처리기가 문서를 그리는 동안 "불러오는 중" 표시를 앱이 그릴지 정한다.

## 검토한 대안

- 설치된 MS Office를 화면 없이 띄워 PDF로 변환한 뒤 PDF 미리보기로 보기(추천안이었다): 충실도가 높고 웹 안에 들어오지만 Office를 매번 띄워야 하고 PDF 변환 캐시가 필요하다. 사용자가 네이티브 처리기를 선택했다.
- 웹뷰용 JS 렌더러: Office 없이도 되지만 pptx·xlsx 충실도가 떨어지고 번들이 커진다(ADR-0014가 이미 버린 대안).
- 별도 창으로 뜨는 시스템 미리보기(Finder의 Space 같은 것): Windows에는 기본 제공 창이 없고, 항목을 방향키로 넘기는 앱 안 미리보기 흐름과 따로 논다.
- 처리기 창을 그림으로 캡처해 겹침 자리를 채우기: 처리기마다 캡처가 실패할 수 있고 구현이 늘어, 겹치는 동안 숨기는 것으로 대신했다.
