# ADR-0021. Twin Deck Remote: 앱 안의 SSH/SFTP 서버와 원격 셸

- 상태: Accepted
- 날짜: 2026-10-16

## 맥락

이슈 #72는 화면 공유 없이 다른 PC의 Twin Deck을 이쪽 Twin Deck에서 같은 방식으로 다루고 싶다고 했다(복사·이동·삭제·이름 바꾸기, 문서는 로컬로 가져와 보기). [ADR-0019](0019-remote-fs-in-process.md)로 SFTP·FTP 클라이언트는 이미 있다. 이번 결정은 Twin Deck이 서버 역할도 하게 하는 범위와 보안 기준이다.

## 결정

- **프로토콜은 SSH/SFTP다.** 앱 안에 `russh` 기반 SSH 서버(`td-remote`의 `server` 모듈)를 두고 SFTP 서브시스템과 PTY 셸 채널을 제공한다. 자체 프로토콜은 만들지 않는다. 기존 SFTP 클라이언트가 그대로 Twin Deck 클라이언트가 되고 일반 `sftp`·`ssh`로도 접속된다.
- **서버는 기본 꺼짐, 수신 주소 기본 `127.0.0.1`이다.** 외부에서 받으려면 사용자가 설정의 `연결 > Twin Deck Remote` 탭에서 주소를 바꾼다. 비밀번호가 없거나 루트 폴더가 비어 있으면 켜지지 않는다.
- **인증은 비밀번호 하나다.** 비밀번호는 OS 키체인에 두고 설정 파일에는 쓰지 않는다. 서버 호스트키는 앱 데이터 폴더에 파일(unix 0600)로 만들어 재시작해도 지문이 같다. 공개키 인증은 하지 않는다.
- **공유 범위는 사용자가 고른 루트 폴더 아래뿐이다.** `..`·절대경로·심볼릭 링크로 루트 밖으로 나가는 요청은 거부하고, 루트 밖을 가리키는 링크는 목록에서 숨긴다. 쓰기(`allow_write`)와 셸(`allow_shell`)은 각각 따로 켜야 하고 기본은 꺼짐이다. 권한·시간 변경(setstat)은 지원하지 않는다.
- **원격 터미널은 SSH 셸 채널이다.** 서버는 `td-terminal`로 셸을 띄우고, 클라이언트는 기존 터미널 화면을 재사용한다. 활성 패널이 `sftp://` 경로일 때 기존 터미널 열기 액션이 원격 셸을 연다(새 키 없음). Service는 twindeck와 일반 SFTP 연결을 구분하지 않으므로 SFTP 연결이면 모두 허용하고 FTP는 거부한다.
- **접속 주소 목록은 `remote.servers`에 `protocol = "twindeck"` 항목으로 둔다.** 연결은 SFTP와 같은 경로를 쓰고(기본 포트 2222), 경로 표기도 `sftp://<id>/…`다. 설정 탭은 자기 protocol 항목만 보이고 다른 항목은 보존한다.

## 이번 범위에서 제외한 것

- **원격 압축·해제.** SFTP에는 서버 쪽 연산이 없다. 내려받아 처리한 뒤 올리는 방식은 별도 과제다.
- **클라이언트의 호스트키 검증(TOFU).** [ADR-0019](0019-remote-fs-in-process.md)의 한계 그대로 서버 호스트키를 확인하지 않고 받아들인다. 외부 주소로 서버를 열면 중간자 공격을 막지 못한다.
- 공개키 인증, 서버 기본 켜짐, `0.0.0.0` 기본 수신.

## 결과

- 장점: 새 프로토콜·인증·전송 코드를 만들지 않았고 기존 파일 작업·큐·충돌 처리를 그대로 쓴다.
- 단점: 비밀번호만으로 외부에 열면 위험하다(호스트키 미검증과 겹친다). 설정을 바꿔도 이미 켜진 서버에는 다시 켜야 적용된다. 원격 셸은 루트 폴더에서 시작하지만 루트에 가두지 않는다. 셸을 허용하면 앱을 실행한 계정의 권한으로 파일 시스템 전체에 닿으므로, 루트 가두기는 SFTP에만 적용된다. 실제 앱 화면과 실제 키체인은 자동 테스트로 확인하지 못했다.

## 검토한 대안

- 자체 TLS+RPC 프로토콜: 서버 쪽 압축·용량 계산을 할 수 있지만 클라이언트·서버·인증·터미널 중계를 모두 새로 만들어야 하고 다른 도구와 호환되지 않는다.
- 공개키 인증 전용: 더 안전하지만 키 등록 UI가 늘어난다.
