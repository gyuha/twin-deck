# M2 벤치마크: 10만 항목 디렉터리

측정일 2026-09-29. 근거: docs/00 §3 "대용량 디렉터리(가설: 10만 항목)에서 UI가 멈추지 않는다", docs/11 M2 "10만 항목 디렉터리의 열기와 스크롤, 정렬 시간을 측정해 임계값을 정하고 문서에 기록한다. 임계값을 넘으면 원인 분석 후 다음 단계로 간다."

## 측정 환경

| 항목 | 값 |
|---|---|

| OS | macOS 26.4.1 (25E253), APFS 로컬 SSD |
| Rust | rustc 1.88.0, **release 빌드**(Rust 측정) |

| 데이터 | 임시 디렉터리에 빈 파일 99,000개 + 폴더 1,000개, 이름은 `item-NNNNNN`(순서를 섞어 생성) |

Windows와 Linux에서는 측정하지 못했다. 특히 WebKitGTK의 렌더링 성능은 docs/03이 알려진 위험으로 적어 둔 부분인데 확인하지 못했다.

## 측정값 (3회 실행의 중앙값)

| 단계 | 시간 | 비고 |

### 화면 (jsdom, 실제 웹뷰 아님)

| 항목 | 값 |
|---|---|
| 앱이 10만 항목 폴더를 열어 첫 목록을 그리기까지 | 169 ms (실행별 167~170 ms) |

| `End`(맨 끝으로) 이동 후 커서 행이 그려지기까지 | 30 ms (실행별 29~60 ms), 그때도 DOM 행은 28개 |
| 크기 정렬 액션이 반영되기까지 | 34 ms (실행별 32~34 ms) |

jsdom에는 레이아웃과 페인트가 없다. 위 화면 값은 "스토어와 React가 10만 항목에서 하는 일"의 비용이고, 웹뷰가 실제로 그리는 시간은 들어 있지 않다.

## 가설 임계값과 판정

임계값은 이 문서가 세운 가설이다 `[낮음]`. 사람이 기다리는 시간의 일반적인 감각(1초 안에 열림, 정렬은 즉각적으로 느껴지는 수준에 가까움)에서 잡았고 사용자 조사나 Marta 비교로 확인한 값이 아니다.

| 기준 (가설) | 측정 | 판정 |
|---|---|---|
| 폴더 열기(조회 + 정렬 + 직렬화 + 파싱 + 스토어 정렬)가 1000 ms 이내 | 357 + 34 + 23 + 71 + 63 = **약 550 ms** (수정 전 정렬이면 약 1230 ms) | 만족. 단 IPC 전송 시간과 웹뷰 렌더는 포함되지 않았다 |
| 정렬이 300 ms 이내 | Rust 34 ms(수정 전 711 ms), JS 15~143 ms | 만족 (수정 후) |
| 화면에 그리는 행 수가 200개 이하이고 목록 크기와 무관 | 28개 | 만족 |
| 스크롤 중 프레임이 끊기지 않음(60fps) | **측정하지 못함** | 판정 보류 |
| 메인 스레드가 오래 멈추지 않음(50 ms 이상 연속 작업이 없음) | 열 때 `JSON.parse` 71 ms와 정렬 63~143 ms가 각각 50 ms를 넘는다 | **기준 미달.** 열 때 한 번씩 생기는 지연이고 스크롤 중에는 없다. 개선안은 아래 |

**결론.** 로컬 macOS에서 10만 항목을 열고 정렬하는 시간은 가설 임계값 안에 들어온다. 하지만 "UI가 멈추지 않는다"는 성공 기준은 절반만 확인됐다. 스크롤 프레임과 IPC 전송, 실제 웹뷰 렌더를 측정하지 못했고, 폴더를 여는 순간 메인 스레드가 약 150~280 ms 연속으로 묶인다. 최종 판정은 실제 Tauri 창에서 측정한 뒤에 한다.

## 원인 분석과 조치

- **Rust 정렬 711 ms → 34 ms.** 임계값(300 ms)을 넘어서 원인을 분석했다. `sort_entries`가 비교할 때마다 `compare_names`로 이름을 정규화하고 소문자로 바꾸며 문자열을 새로 할당했다. 10만 항목의 정렬은 비교가 약 170만 번이고 비교마다 문자열 2개를 만든다. `sort_by_cached_key`로 키를 항목마다 한 번만 만들도록 바꿨고 정렬 결과는 그대로다(`sort_entries_matches_compare_names_semantics`가 이전 방식과의 동일성을 검사한다). 이 조치는 이 태스크에서 했다.
- **정렬이 두 번 일어난다.** Rust `list_dir`가 이름순으로 정렬해서 보내고, 스토어가 탭의 정렬(`effectiveSort`)로 다시 정렬한다. 기본 정렬일 때는 중복이다. 손대지 않았다 — 정렬 방향과 기준이 탭마다 달라 스토어 쪽이 어차피 필요하고, Rust 정렬은 이제 34 ms다.
- **메인 스레드 지연(`JSON.parse` 71 ms + 정렬 63~143 ms).** 아직 손대지 않았다. 후보: 페이로드를 줄이기(사용하지 않는 컬럼의 필드를 빼기, 경로를 항목마다 싣지 않고 폴더 경로와 이름으로 조합), 정렬과 파싱을 Web Worker로 옮기기, Rust에서 정렬 기준까지 받아 정렬해서 보내기. 실제 웹뷰에서 측정해 문제가 확인되면 착수한다.
- **목록 조회 357 ms.** `symlink_metadata` 시스템 호출이 항목마다 한 번 일어나는 비용이다(항목당 약 3.6 µs). 디렉터리 열기의 가장 큰 항목이지만 그대로 두었다.

## 측정하지 못한 것

- Tauri IPC의 실제 전송 시간(약 16 MiB JSON이 웹뷰로 넘어가는 시간), 웹뷰의 실제 렌더와 스크롤 프레임, 메모리 사용량.
- Windows, Linux, 그리고 macOS의 다른 파일시스템(외장 디스크, 네트워크 볼륨).
- 파일 감시 이벤트가 몰릴 때(10만 항목 폴더에서 대량 변경)의 갱신 비용. 지금은 이벤트마다 목록을 통째로 다시 읽는다.
- 가상 스크롤의 스크롤 성능 자체. 테스트는 "그려지는 행 수"와 "커서 이동 시 그 행이 그려지는지"만 확인한다.
