# 실행 기록 — 복사·이동·삭제 작업이 빨리 실패하면 사용자에게 오류를 알린다 (UI)

- S3 `trackTransfer`가 진행 창 없이 끝나는 분기에서 실패를 알림으로 올림 — ✅ as planned
- S4 문서 — ✅ `docs/07-ui-spec.md` 큐 항목에 한 줄 추가

## DoD 기준값 → 실행 후
1. `cd apps/desktop && bunx vitest run` → 수정 전 기준 전부 통과(기준선) → **151 파일 / 1236 테스트 통과**. `bunx tsc --noEmit` → 통과. 루트 `bun run test`(모든 워크스페이스)도 통과.
2. 새 테스트(휴지통·복사 즉시 실패 시 사유가 알림에 들어 있음, 한국어 문구) → 3 빨강 → 초록.
3. 성공한 작업은 알림 없음 → 테스트로 확인(수정 전·후 통과). 사용자가 닫아 둔 진행 창을 다시 띄우지 않는 기존 동작은 코드를 건드리지 않았다(`shownOnce` 분기 그대로).
4. 한 번만 알림 → `실패 알림은 한 번만 뜬다` 테스트가 폴링을 400ms 더 돌려도 알림이 1개임을 확인.

## 결정과 발견
- 고친 곳은 `trackTransfer` 한 곳이다. 휴지통·삭제·복사·이동·압축·추출·미리보기 삭제가 모두 이 함수를 거치므로 한 번에 덮인다. 다만 테스트는 휴지통과 복사만 직접 확인했다. 압축·추출·미리보기 삭제는 같은 함수를 지나지만 직접 시험하지 않았다.
- 알림 문구: `{verb} 실패: {경로}: {사유}` (여럿이면 ` (외 N건)`). 사유는 큐 패널·진행 창과 같은 `rustText`로 영어 번역이 적용된다. 영어는 `Deleting failed: …`처럼 현재진행형 동사가 앞에 와서 다소 어색하다(`verb`가 진행 창 제목용 문구를 재사용하기 때문). 고치려면 동사 키를 따로 만들어야 해서 범위 밖으로 두었다.
- `queueJobs()`가 예외를 내면 `catch { return }`로 조용히 끝나는 기존 동작은 그대로 뒀다. 이 경로는 백엔드 IPC 자체가 깨진 경우라 "작업이 빨리 실패"와 다른 문제이고, 알림을 띄워도 사유를 알 수 없다. 필요하면 별도 작업이다.
- **#142와의 교차 발견**: 전체 vitest에서 `i18n-rust-messages.test.ts`가 실패했다. #142가 `error.rs`에 추가한 한국어 오류 문구 3개가 `apps/desktop/src/i18n/rust.ts` 대응표에 없어서였다(Rust 소스의 모든 한국어 리터럴이 대응표에 있어야 하는 테스트). 영어 번역 3줄을 `rust.ts`에 추가해 해결했고, 이 사실을 #142의 `run.md`에도 적었다. #142의 `cargo` 검증만으로는 잡히지 않는 실패였다.

## 검증하지 못한 것
- 실제 Tauri 런타임과 WKWebView에서 알림이 보이는 모습은 눈으로 확인하지 못했다(vitest + FakeBackend 한정). 실제 백엔드의 큐 지연과 FakeBackend의 즉시 모드는 다르다.
- 진행 창을 사용자가 직접 닫은 뒤(`shownOnce`) 실패한 경우는 코드 경로상 알림이 뜨지만 별도 테스트는 없다.
