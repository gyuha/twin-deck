# 2026-10-14 — 터미널 한글 출력과 글꼴 간격 (이슈 #61)

## 계획과 실제
- PTY 인코딩과 글꼴 계측을 분리해 조사하고 수정했다. locale 없는 GUI 환경 및 C/POSIX 기본값은 자식 PTY에서 UTF-8로 보완하고, 명시적인 지역·기존 인코딩 설정은 보존한다.
- 사용자 글꼴에 고정폭 대체 목록을 붙이고 로드 완료 후 폭을 측정한다. 변경 시 재계측하며 이전 비동기 요청과 해제 후 갱신을 차단한다.
- 실제 macOS PTY와 Chromium xterm에서 한글 출력을 확인했다. 같은 760px에서 기본·Jetendard·없는 글꼴의 대체 경로는 95칸, 실제 Wanted Sans는 55칸이었다. Wanted Sans의 비고정폭 간격은 남으며 설정 설명에 안내했다.
- 전체 JS 1,380개·Rust 13개, 타입·clippy·fmt 검사를 통과했다. 글꼴 로드용 비표시 표본이 UI 문구 검사에 걸려 1회 수정했다. 검사 규칙은 그대로 두고 표본 표현만 유니코드 이스케이프로 바꿨다.
- 네이티브 WKWebView 화면 및 Windows 실행은 미검증이다. 브라우저 검증을 네이티브 전체 검증으로 확대 해석하지 않는다.

## 학습
- 한글이 물음표로 보이면 폰트 교체 전에 PTY의 실제 바이트와 유효 locale을 비교한다. 이번에는 ls가 C 환경에서 이미 물음표를 출력하므로 렌더러만 고쳐서는 해결되지 않았다.
- 설치되지 않은 글꼴의 대체 결과와 실제 비고정폭 글꼴의 간격을 구분한다. 전자는 고정폭 fallback으로 보완할 수 있고, 후자는 터미널의 칸 구조상 간격이 남는다.
- 폰트 로드가 비동기라면 계측 시점뿐 아니라 설정 변경 순서와 엔진 종료도 함께 검증한다. 실제 화면에는 NFC·NFD, UTF-8 청크 경계, 크기 변경을 포함한다.
- 다음에는 글리프 로드용 비표시 표본을 넣을 때 UI 문구 검사도 함께 실행한다. 검사 allowlist를 넓혀 실패를 숨기지 않는다.
- locale 수정은 새 터미널 세션에 적용되며, 셸 초기화 파일의 재설정은 별도 원인으로 확인한다.
