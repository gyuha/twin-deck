# 2026-10-13 — 코드 리뷰 지적 4건을 고친다 (압축 임시 파일 혼입 · 치워 둔 이름 · 성능 · 이동 순서)

## Plan vs actual
- What went as planned: 코드 리뷰 지적 7건을 코드로 확인해 4건(1·2·4·7)만 수정하고 3·5·6은 근거와 함께 기각했다. S2(`compress_skipping`)·S3(보이는 임시 이름)·S4(`is_within` 정리)·S5(원본 삭제 뒤에 옛 대상 버리기) 모두 계획대로 들어갔고 `cargo test --workspace` 349개, `bun run test` 전체, clippy·fmt·tsc가 통과했다.
- Divergences:
  - **빨강 테스트 2개가 잘못된 이유로 실패하고 있었다.** 테스트 가짜 `NoRenameFs`가 모든 `rename`을 막아서, 이동·이름 테스트가 치워 두기 단계에서 먼저 실패했다(옛 대상이 그대로 남아 빨강). 수정이 아니라 가짜가 원인이었다. 가짜를 "같은 폴더 안 rename은 통과"로 현실에 맞춘 뒤, 수정본의 두 조각만 임시로 되돌려 올바른 이유(남은 항목 0개 = 옛 대상이 이미 지워짐)로 실패함을 확인하고 복원했다.
  - **계약을 확정한 뒤 6번이 사라졌다.** 빈 오류 목록으로 `failed`가 되는 경로가 큐(`queue.rs:456`)와 `FakeBackend` 어디에도 없어서 코드 변경 없이 기각했다. 계약의 "수정" 목록에 있던 항목을 뒤에 바꿨으므로 보고에 그 사실을 적었다.
  - 1번(압축)은 대안 "압축 뒤에 치우기"가 옛 zip을 새 zip에 넣는 문제를 그대로 남겨서 기각하고, 치워 둔 경로를 압축기의 건너뛰기 목록에 넣는 쪽으로 갔다. 압축기가 대상이 있으면 `Exists`로 거부하는 것이 이 선택의 근거였다.

## Learnings
- Do differently next time:
  - **빨강 확인은 "실패했다"가 아니라 "예상한 이유로 실패했다"까지 본다.** 새 테스트가 실패 메시지(어느 단언에서, 어떤 값으로)를 계획이 말한 결함과 대조해 읽는다. 이번처럼 테스트 가짜가 먼저 막아서 난 빨강은 수정이 맞는지 아무것도 증명하지 못한다. 의심스러우면 수정의 해당 부분만 임시로 되돌려 올바른 이유로 실패하는지 본다.
  - **계약을 좁히는 수정 옆의 테스트 가짜는 "실제가 하는 일"을 하는지 먼저 본다.** `NoRenameFs`는 "교차 볼륨에서 rename 실패"를 흉내 내려던 것인데 같은 폴더 안 rename까지 막고 있었다. 이전 계획(`ops-overwrite-safety-fix`)에서도 이 가짜의 오류 종류가 넓은 가정이어서 한 번 고쳤다. 같은 가짜를 두 번 고쳤으니 다음에 이 가짜를 쓰는 테스트를 추가할 때는 가짜가 어떤 동작을 허용하는지 주석을 읽고 시작한다.
  - 리뷰 지적은 코드로 확인한 뒤 고친다. 7건 중 3건은 기각됐고 1건은 일부만 맞았다. 확인 없이 전부 고쳤다면 하드 링크 거부를 풀어 `fs::copy` 데이터 손실을 만들 뻔했다.
  - 계약 질의 뒤에 새 사실이 나와 항목이 바뀌면(6번처럼) 최종 보고에서 계약과 달라진 점을 숨기지 말고 첫머리에 적는다.
- **확인하지 못한 채 남은 것:** 실제 교차 볼륨(EXDEV) 이동은 가짜로만 시험했고, Windows는 컴파일 검증뿐이다. 원본 삭제가 실패해 옛 대상이 `x.txt.td-replaced-…`로 남는 경우 사용자가 이를 어떻게 정리하는지는 정해져 있지 않다.
