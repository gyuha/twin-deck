# 2026-10-01 — 복사/이동 확인 창과 복사/이동/삭제 진행 창

## 계획 대비 실제
- 계획대로 된 것: 파일 단위 진행 집계(S1), `JobDto`와 bindings(S2), 확인 창(S3), 진행 창(S4). 자동 테스트 기준 DoD 1~7은 처음부터 통과했다.
- 차이:
  - 실제 앱 확인(UAT)에서 결함이 네 번 나왔다. ① 완료 후 대상 목록이 안 보임 ② 파일이 많으면 진행 창과 갱신이 안 됨 ③ 이벤트 합치기로도 그대로 ④ 삭제에는 진행 창이 없음. 가짜 백엔드 테스트는 전부 초록이었다.
  - ①은 `reload`에 순서 보호가 없어 옛 목록이 덮어쓰는 경합이었고 재현해서 고쳤다. ②는 "큐 이벤트가 몰려서"라고 추정하고 100ms 합치기(`coalesce`)를 넣었지만 증상은 그대로였다. 증거 없이 세운 추정이었다.
  - 실제로 통한 것은 ③의 수정이다. UI가 전송 중에 `queueJobs()`를 직접 조회하고, 끝나면 `reloadAll()`을 명시적으로 부르는 방식이다. 이벤트가 웹뷰에 닿는지는 끝까지 확인하지 못했다(`docs/m1-status.md:42`가 이미 "실제 Tauri 런타임 왕복은 검증하지 않았다"고 적고 있었다).
  - 범위가 늘었다: 복사/이동만이던 것이 사용자 요청으로 영구 삭제와 휴지통까지 갔다. 삭제는 로컬이면 파일 단위 순회, 아카이브 안은 한 번에, 휴지통은 항목 단위다.
  - `core.copy.to_inactive`가 OP-10("대화상자 없음")이라 확인 창을 거치지 않게 보존했다. 기존 테스트 약 25개에 Return을 넣었고, 다크 테마 토큰 `--color-neutral-200`을 추가했다.

## 배운 것
- 다음에는 이렇게:
  - 이벤트/IPC처럼 실제 런타임에서 검증된 적 없는 경로에 기능이 기대면, 계획 단계에서 그 사실을 DoD의 실제 앱 확인 항목으로 못 박고 "이벤트에 기대지 않는" 설계를 기본으로 한다. 이번에는 fake만 초록이라 세 번 돌아갔다.
  - 실제 앱에서만 재현되는 결함은 추정으로 고치기 전에 사용자에게 증거 3가지(대상에 실제로 있는지, 콘솔 오류, 작업 목록 상태)를 먼저 받는다. 추정 수정(`coalesce`)은 효과가 없었다.
  - fake 백엔드에 "이벤트가 안 오는 모드"(`queueEvents=false`)처럼 실제 장애를 흉내 내는 스위치를 두면 같은 종류의 결함을 테스트로 막을 수 있다.
  - 영향 범위: 확인 창 같은 새 모달을 F5/F6에 끼우면 기존 키보드 시나리오 테스트가 연쇄로 깨진다. 계획 단계에서 `grep F5|F6`로 대상 테스트를 미리 센다.
- 남은 불확실성: 실제 앱에서 큐 이벤트가 오는지는 모른다. 콘솔에 `[twin-deck] 큐 이벤트를 처음 받았습니다`가 한 번 찍히는지로 확인할 수 있다. 안 찍히면 이벤트 경로는 별도 결함이다.
