# 2026-10-15 — HWP·HWPX 쪽 미리보기 (`@rhwp/core`)

## 계획 대비 실제
- 계획대로 된 것: 5개 슬라이스가 모두 들어갔다. 지연 로더, `HwpView`, `Preview.tsx` 연결, 문서 5곳, 실제 앱 확인까지 갔고 사용자가 실제 창에서 잘 됨을 확인했다.
- 차이:
  - 처음 요청의 `ohah/hwpjs`는 그릴링 중 `@rhwp/core`로 바뀌었다. hwpjs는 npm이 rc.10이고 `main`은 Zig 텍스트 전용이었으며, 브라우저 WASM이 공유 메모리·Worker를 요구했다.
  - 워크플로 없이 이 세션에서 직접 실행했다. 변경이 작아 서브에이전트 비용이 이득보다 컸다.
  - 계획 DoD 1 (d)의 "압축 안 경로 제외" 테스트는 쓰지 않았다. EPUB과 같은 `!isArchivePath` 가드로 대신했다.
  - 계획에 없던 `lib/hwp/wasm.d.ts`(`?url` 모듈 선언)가 필요했다. `vite/client` 타입이 tsconfig에 없다.

## 배운 것
- 다음에 다르게 할 것:
  - 외부 라이브러리를 고르기 전에 `npm pack`으로 풀어 보고 `d.ts`와 브라우저 진입점(공유 메모리·Worker 필요 여부)부터 본다. 이번에 hwpjs를 걸러낸 것이 이 확인이었다.
  - wasm 라이브러리는 단위 테스트에서 읽기 계층을 가짜로 바꾸므로 WKWebView 동작을 증명하지 못한다. 그 전에 실제 wasm을 Node에서 실제 파일로 돌려 API 사용이 맞는지 먼저 확인하는 것이 싸다(이번 `noori.hwp` 3쪽 렌더링).
  - 새 뷰어 테스트의 파일 내용에는 NUL을 넣는다. 서비스가 내용으로 "기타"를 판정하는 EPUB·Office 테스트와 같은 관례다.
  - 계획의 DoD에 적은 검사 항목은 빠뜨리지 않는다. (d)를 쓰지 않은 채 넘어갔다.
- 확인된 것: `previewSheet`·`Ctrl+Tab` 재사용으로 새 키 바인딩이나 Rust·브리지 변경 없이 끝났다.
