# 2026-11-03 — 명령어 줄 결과 창 ANSI 색 표시 (#211, 이슈 #157 ②)

## 계획 대비 실제
- 계획대로 된 것: ui의 SGR 해석기(`lib/ansi.ts`)·`AnsiText` 렌더·복사 시 ANSI 제거는 TDD로 계획대로 들어갔다(구현 전 실패 확인).
- 어긋난 것:
  - S1(td-launch 색 강제 환경 변수)을 구현했다가 되돌렸다. review가 측정: 환경 변수는 셸과 모든 하위 프로세스에 상속되어 `git diff > a.patch`(923→1043바이트), `git diff | grep`, 사용자 스크립트 내부 리다이렉트 출력에 ANSI가 섞인다 → 패치 파일 손상. 명령어 줄의 `>`·`|` 검사로도 하위 스크립트 경로는 막을 수 없다.
  - 그 전에 core가 사용자 전역 `color.diff=auto`가 `color.ui=always`보다 우선함을 발견해 7개 키로 넓혔으나 같은 이유로 함께 되돌렸다.
  - 목표 축소(사용자 결정): 결과 창은 명령이 스스로 낸 색만 칠한다(`git diff --color`). 자동 색은 #212 터미널 팝업이 맡는다.
  - review 지적으로 해석기 범위를 넓혔다: OSC·2바이트 ESC 제거, `\r` 덮어쓰기.

## 배운 점
- 다음에 다르게 할 것:
  - "출력의 모양을 바꾸려고 자식 프로세스 환경을 바꾸는" 설계는 그 환경이 화면이 아닌 출력(파일·파이프·하위 스크립트)에도 상속된다는 점을 grilling 단계에서 시나리오(`cmd > file`, 스크립트 안의 리다이렉트)로 검사한다. 이번 grilling 질문 6에서 이 시나리오를 묻지 않아 추천이 틀렸다.
  - TTY 여부로 색을 정하는 도구의 동작을 바꾸고 싶으면 환경 강제가 아니라 pty(도구가 fd별로 판단)를 쓰거나, 사용자가 명시적으로 옵션을 붙이게 한다.
  - 사용자 실제 환경(전역 git 설정)이 테스트 격리 때문에 가려졌다 — 통합 테스트를 격리해 통과시킨 부분이 곧 실제 사용 경로의 실패였다. 격리할 때는 "실제 사용자 설정에서도 성립하나"를 따로 확인한다.
